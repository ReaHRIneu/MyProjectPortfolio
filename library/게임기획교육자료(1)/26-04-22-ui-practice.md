# 게임 UI 기획

플레이어의 경험을 설계하는 핵심 역량

## UI 설계 용어

UI 기획 실무에서 반드시 알아야 할 핵심 용어들이다. 각 단계는 기획의 구체성과 완성도를 높이는 방향으로 순차적으로 적용된다.

#### 와이어 프레임 (Wireframe)

화면 레이아웃을 표시하기 위한 UI 배치도. 시각적 요소보다 구조와 기능 배치에 집중하는 초기 설계 단계이다.

#### 목업 (Mockup)

실제와 흡사한 정적인 형태의 모형. 와이어프레임보다 시각적으로 완성도가 높으며 디자인 검토에 활용된다.

#### 스토리보드 (Storyboard)

정책, 절차, 와이어프레임, 설명 등이 모두 포함된 종합 문서. 기획 의도와 상호작용 흐름을 개발팀에 전달하는 핵심 산출물이다.

#### 프로토타입 (Prototype)

다양한 인터렉션이 결합되어 실제 서비스처럼 작동하는 모형. 사용성 테스트와 이해관계자 리뷰에 활용된다.

## 스케일폼 (Scaleform)

게임 UI 개발에 널리 사용되는 미들웨어로 플래시(Flash)와 액션스크립트(ActionScript) 기반으로 동작한다. 언리얼 엔진, 크라이엔진에 기본 내장되어 있으며, 기타 3D 게임 엔진과도 통합하여 사용할 수 있다.

#### 엔진 통합

언리얼 엔진과 크라이엔진에 스케일폼이 기본 내장되어 있어 별도의 설치나 라이선스 구매 없이 즉시 사용할 수 있다.

#### 기반 기술

스케일폼은 어도비 플래시 기술을 게임 UI 개발에 활용할 수 있도록 설계된 미들웨어이다. 디자이너는 Adobe Flash Professional(현 Animate)에서 UI를 제작하고 .swf 파일로 내보내면, 개발자는 이를 게임 엔진에서 바로 불러와 사용할 수 있어 디자이너-개발자 간 협업 워크플로우가 효율적이다.

#### 3D 지원

스케일폼은 단순한 2D 평면 UI를 넘어 3D 공간에 UI를 배치하고 렌더링할 수 있는 기능을 제공한다. UI요소를 3D 월드 공간에 직접 삽입하거나(World Space UI), 게임 오브젝트에 부착하는 방식으로 몰입감 있는 인터페이스를 구현할 수 있다.

## UI 기획 순서

체계적인 UI 기획은 거시적인 흐름 파악에서 시작해 개별 페이지의 세부 요소까지 단계적으로 구체화하는 하향식 접근법을 따른다

#### 상황 리스트 정리

UI가 필요한 모든 상황 파악. 게임 흐름(시작, 로비, 인게임, 종료 등)에 따라 UI가 등장하는 모든 시점을 빠짐없이 목록화한다. 목록을 바탕으로 와이어 프레임을 작성한다.
게임 예시 : 리그 오브 레전드의 경우 - 로그인, 챔피언 선택, 인게임 HUD, 상점, 결과 화면, 설정 등 수십 개의 UI 상황을 사전에 목록화한다.

#### 상황별 기획

페이지 리스트 및 연결도 작성. 각 상황에서 필요한 페이지를 정의하고, 페이지 간 이동 흐름(플로우)을 연결도로 시각화한다.
게임 예시 : 모바일 RPG의 경우 - 메인 로비 → 던전 입장 → 전투 → 보상 수령 → 로비 복귀로 이어지는 페이지 연결도를 작성한다.

#### 페이지별 기획

컨셉·스토리보드·세부 요소 정의. 개별 페이지의 UI 컨셉, 와이어프레임, 스토리보드, 컴포넌트 상세 정보를 문서화한다.
게임 예시 : 배틀그라운드의 인벤토리 UI - 아이템 슬롯 개수, 드래그 앤 드롭 인터랙션, 장착/해제 상태, 무게 제한 표시 등을 스토리보드로 상세 정의한다.

각 단계는 이전 단계의 산출물을 기반으로 하므로, 앞 단계에서 누락이 발생하면 이후 작업 전체에 영향을 준다. 꼼꼼한 초기 정리 핵심이다.

## UI가 필요한 상황 정리

UI 기획의 첫 단계는 게임 내 UI가 필요한 모든 상황을 빠짐없이 파악하는 것이다. 머리 속으로만 생각하면 중요한 상황이나 페이지가 누락될 가능성이 높으므로, 반드시 문서화하여 정리해야 한다. 비슷한 장르나 플랫폼의 타 게임을 참고하는 것이 편리하다.

#### 게임 흐름에 따른 분류 (리그 오브 레전드)

- 시작 / 로그인 (서버 선택, 계정 로그인 화면 등)
- 로비 / 캐릭터 선택 (매칭 시스템, 밴픽 등)
- 인게임 / 배틀 (스킬창, 아이템창, 킬로그 등)
- 마을 / 종료 (게임 결과 창, 로비 등)

#### 흐름 별 기능 분류 예시 (리그 오브 레전드)

- 로비 : 상점(챔피언, 스킨) 관련 기능, 게임 모드(일반, 랭크, 칼바람) 선택 관련 기능, 친구 초대 관련 기능 등
- 인게임 : 상점(구매, 판매) 관련 기능, 미니맵 오브젝트 표시 기능, 스킬창 관련 기능, 킬로그 관련 기능
- 게임 종료 : 게임 결과 창 관련 기능 (클릭한 챔피언 성적 확인 등)

## 페이지 정리

상황 리스트 파악이 완료되면, 이를 바탕으로 실제 구현할 UI 페이지 목록을 체계적으로 정리한다. 단순한 목록 작성에 그치지 않고 각 페이지 간의 이동 경로와 연결 조건까지 명확히 문서화하는 것이 핵심이다.

#### UI 페이지 리스트 정리

상황 리스트를 바탕으로 필요한 모든 UI 페이지를 누락 없이 목록화한다.
게임 예시 : 로스트아크의 경우 - 캐릭터 선택, 마을 로비, 던전 입장, 레이드 대기실, 경매장, 우편함, 설정 등 수십 개의 페이지를 사전에 목록화한다.

#### 페이지 연결도 작성

각 페이지 간의 이동 흐름과 해당 이동이 발생하는 조건(버튼 클릭, 이벤트 발생 등)을 시각적으로 정리한다.
게임 예시 : 모바일 RPG(예 : 브라운더스트2) - 메인 로비 → [전투 입장 버튼] → 스테이지 선택 → [시작] → 전투 화면 → [결과 팝업] → 보상 수령 → 로비 복귀 흐름을 연결도로 표현한다.

#### 예외 케이스 고려

팝업, 알림, 에러 화면 등 일반 흐름에서 벗어나는 예외 케이스도 함께 정의한다.
게임 예시 : 배틀그라운드 - 게임 도중 네트워크 끊김 시 재접속 팝업, 아이템 획득 한도 초과 시 경고 알림, 매칭 실패 시 에러 메시지 등을 별도로 정의한다.

## UI 컨셉 기획

*페이지별 기획의 첫 단계*로, 해당 UI에서 다루어야 할 정보와 기능의 본질을 정의한다. 이 단계에서 충분한 고민 없이 스토리보드로 넘어가면 이후 수정 비용이 크게 증가한다.

#### 입출력 정보 정의

해당 UI 화면에서 입력(Input)되어야 하는 정보와 출력(Output)되어야 하는 정보는 무엇인가? 플레이어가 제공하는 정보와 시스템이 제공하는 정보를 명확히 구분한다.
예 : 원신 상점 UI - 입력 : 플레이어가 선택한 아이템, 보유 재화 / 출력 : 구매 가능 여부, 아이템 상세 정보, 구매 후 잔여 재화.

#### 표현 방식 결정

해당 정보는 어떤 방식으로 표현되어야 하는가? 텍스트, 아이콘, 게이지, 리스트 등 UI 컴포넌트 선택의 근거를 마련한다.
예 : 리그 오브 레전드 HUD - 체력/마나는 게이지 바, 스킬 쿨타임은 아이콘 + 숫자 오버레이, 킬/데스/어시스트는 텍스트 수치로 표현.

#### UI 개론 원칙 적용

가시성, 일관성, 직관성, 접근성 등 UI 개론에서 배운 원칙을 바탕으로 해당 UI의 컨셉 방향을 정리한다.
예 : 배틀그라운드 인벤토리 - 가시성(아이템 아이콘 크기 통일), 직관성(드래그 앤 드롭으로 장착), 일관성(모든 슬롯 동일한 격자 구조), 접근성(색맹 모드 지원).

## 스토리보드 / 세부 UI 기획

UI 컨셉이 확정되면 와이어프레임을 기반으로 실제 개발에 사용되는 스토리보드를 제작한다. 스토리보드는 기획자와 개발자, 디자이너가 공유하는 가장 중요한 커뮤니케이션 도구이다.

#### 와이어프레임 기반 제작

확정된 와이어프레임을 기반으로 구체적인 스토리보드를 작성한다.
예 : 로스트아크 캐릭터 선택 화면 - 와이어프레임에서 캐릭터 목록 슬롯 배치, 스탯 표시 영역, 서버 선택 드롭다운 위치를 먼저 확정한 뒤 스토리보드로 발전시킨다.

#### UI 간의 연결 정의

각 화면 간 이동 흐름과 전환 조건을 명확히 기술한다.
예 : 모바일 RPG (예 : 에픽세븐) - 메인 로비의 [전투] 버튼 클릭 시 스테이지 선택 화면으로 전환, 뒤로가기 버튼 클릭 시 로비 복귀, 스테이지 클리어 시 결과 팝업 표시.

#### 컴포넌트 위치 크기 기능

각 UI 컴포넌트의 위치, 크기, 역할을 수치와 함께 정확히 정리한다.
예 : 배틀그라운드 HUD - 체력바 : 좌하단, 너비 200px, 높이 16px / 탄약 표시 : 우하단, 현재/최대 탄약 텍스트 / 미니맵: 우하단, 150x150px 원형.

#### 액션 및 상태 정리

각 컴포넌트의 인터렉션 방식과 Normal, Focused, Pressed, Disabled 등의 상태를 상세히 기술한다.
예 : 디아블로4 스킬 버튼 - Normal(사용 가능), Focused(마우스 오버 시 툴팁 표시), Pressed(클릭 시 발동 애니메이션), Disabled(마나 부족 시 회색 처리 + 잠금 아이콘)

## 스토리보드 예시 - 웹 페이지 UI 기획

실제 스토리보드 예시이다. 좌측에는 와이어프레임으로 레이아웃을 시각화하고, 우측에는 각 컴포넌트(로고, 네비게이션, 날씨 위젯, 뉴스 아이템, 비디오 플레이어 등)에 대한 상세 설명을 병기한다. 기획 의도가 명확하게 전달되어야 한다.

*(이미지 생략: 웹 페이지 스토리보드 예시 이미지 6점)*

> 스토리보드는 기획자·디자이너·개발자 모두가 공유하는 계약서와 같다. 모호한 표현은 반드시 구체적인 수치나 조건으로 대체한다.

## 스토리보드 - 게임 월드 내 UI 포함

게임 내에서 기획해야 하는 UI는 화면 최상단의 HUD만이 아니다. 게임 오브젝트와 게임 월드 안에 표시되는 다양한 UI요소들도 모두 기획 범위에 포함된다.

#### 캐릭터 명 표시

플레이어 캐릭터 및 NPC 위에 표시되는 이름 태그, 길드 이름, 레벨 점보 등을 포함한다.

#### 채팅 말풍선

게임 월드 내에서 캐릭터 주변에 표시되는 말풍선 UI. 텍스트 길이와 표시 시간을 함께 정의한다.

#### 이동 지역 가이드

플레이어의 이동 목적지, 퀘스트 마커, 위험 구역 경계 등 게임 월드에 오버레이되는 가이드 UI이다.

## UI 기획·역기획은 최고의 기획 훈련

UI 기획과 역기획은 시스템 기획자로 성장하기 위한 가장 효과적인 훈련 방법 중 하나이다. 구조와 규칙이 타 시스템에 비해 명료하고, 예측하기 힘든 예외 상황의 발생이 제한적이기 때문이다.

> 역기획 (Reverse Planning) : 완성된 게임의 UI를 분석하여 기획 의도와 설계 구조를 재현하는 훈련이다. 분석력과 문서화 능력을 동시에 키울 수 있다.

# UI 기획 참고 요소

플랫폼별 UI 컴포넌트와 인터랙션 방식을 이해하면 더 체계적인 기획이 가능하다.

# PC UI 컴포넌트 리스트

PC 게임 UI 기획 시 반드시 숙지해야 할 표준 UI 컴포넌트 목록이다. 각 컴포넌트는 고유한 동작 방식과 상태를 가지며, 기획 문서에서 이를 명확히 정의해야 한다.

*(이미지 생략: PC UI 컴포넌트 리스트 이미지)*

## 컴포넌트 별 정리 정보

각 UI 컴포넌트의 특성에 따라 기획 문서에 기재해야 할 정보의 종류가 달라진다. 빠짐없는 정보 정의가 개발 단계에서의 혼선을 방지한다.

#### 텍스트 표시 컴포넌트

사이즈, 폰트, 색상, 최대 표시 글자 수, 줄 바꿈 여부, 초과 시 처리(말줄임표, 자동 줄바꿈, 스크롤 바)를 정의한다.
**폰트 종류**는 클리어타입/이미지 폰트 등 렌더링 방식까지 구분하고, **표기 기준**은 px단위로 명시한다. **색상**은 HEX 코드로 고정하며, 자간·행간도 함께 기록한다.
예 : 닉네임 최대 12자, 아이템명 최대 20자처럼 컴포넌트별 최대 글자 수를 정의하고, 초과 시 처리 방식을 정한다.
다국어 대응이 필요한 경우 한/영/일 언어별 폰트 교체 정책과 대체 폰트 우선순위를 정한다.
예시 : 배틀그라운드 킬 피드 - 흰색 텍스트, 최대 15자, 3초 후 페이드 아웃

#### 인터랙션 컴포넌트 (버튼 등)

기본적으로 **Normal, Focused, Pressed, Disabled**의 4가지 상태를 정리한다.
**Normal**은 기본 색상, 테두리, 아이콘 표시 여부를 포함한다.
Focused는 마우스 오버 또는 게임패드 포커스 시 변화로, 밝기 증가와 테두리 강조, 툴팁 표시 여부를 명시한다.
**Pressed**는 클릭/탭 반응으로, 크기 축소(scale 0.95), 색상 어두워짐, 클릭 사운드 같은 피드백을 정의한다.
**Disabled**는 비활성 처리로, 회색 처리(opacity 0.4), 클릭 불가, 잠금 아이콘 표시를 포함한다.
예시 : 원신 가챠 버튼 - Normal(금색), Focused(빛나는 테두리), Pressed(눌림 애니메이션), Disabled(재화 부족 시 회색)

#### 기타 요소

이펙트, 툴팁, 사운드 피드백 등의 부가 요소도 함께 정리한다.
**이펙트**는 트리거 조건과 연출 범위를 적고, 예를 들어 버튼 클릭 시 파티클, 레벨업 시 전신 발광처럼 구분한다.
**툴팁**은 표시 조건(예 : 마우스 오버 0.5초 후), 위치(커서 우측 상단), 최대 너비(200px), 표시 내용을 세부적으로 정의한다.
**사운드 피드백**은 버튼 클릭음, 에러 알림음, 획득 효과음 등 상황별로 **사운드 ID**를 분리해 관리한다.
**모바일 진동 피드백**도 포함하며, 버튼 탭 시 약진동(10ms), 에러 시 강진동(30ms)처럼 강도를 구분한다.
예시 : 디아블로4 아이템 툴팁 - 마우스 오버 즉시 표시, 아이템 등급별 색상(일반/희귀/전설), 비교 스탯 자동 표시

#### 사이즈 & 위치 규칙

모든 컴포넌트의 사이즈와 위치는 가능한 **8의 배수**에 맞추고, 최소 짝수 단위로 지정한다.
**버튼 크기**는 160x48px, 여백 16px처럼 실제 수치로 기록해 개발자가 그대로 적용할 수 있게 한다.
모바일에서는 **최소 터치 영역**을 준수해야 하며, 44x44pt(iOS), 48x48dp(Android) 기준을 확인한다.
**해상도 대응**은 기준 해상도 1920x1080을 기준으로 비율 설계 후 다른 해상도에 스케일을 적용한다.
또한 모바일 노치와 홈 인디케이터를 고려한 **Safe Area 침범 금지**를 명시한다.
예시 : LOL HUD - 체력바 200x16px, 스킬 아이콘 64x64px, 미니맵 150x150px, 모두 8의 배수.

## 스마트 디바이스 UI 기획

스마트 디바이스는 다양한 제조사와 모델별로 해상도가 다르기 때문에, PC와는 다른 접근 방식이 필요하다. 타겟 디바이스 범위를 먼저 정의하고 그에 맞는 기획을 진행한다.

#### 해상도별 기획

모든 디바이스를 지원할 수는 없다. 게임의 서비스 타겟에 맞는 몇 개의 대표 해상도를 선택하여 작업한다.

#### 방향 지원 여부 체크

가로(Landscape), 세로(Portrait) 또는 둘 다를 지원하는지 결정하고, 각 방향에 맞는 레이아웃을 별도로 기획한다.

#### 터치 영역 고려

버튼 등 인터랙션 컴포넌트는 터치 영역을 고려해 배치한다. iOS 가이드라인 기준 최소 44x44pt 이상으로 디자인할 것을 권고한다.

#### 짝수 단위 수치 사용

모든 컴포넌트의 사이즈와 위치 값은 짝수 단위로 지정한다. 홀수 값은 디바이스 렌더링 시 픽셀 깨짐 현상을 유발할 수 있다.

## 스마트 디바이스 입력 체계

스마트 디바이스는 PC와 근본적으로 다른 입력 방식을 제공한다. 각 입력 방식의 특성을 UI 기획에 반영하면 더욱 몰입감있는 게임 경험을 설계할 수 있다.

#### PC 디바이스 입력

- 마우스 & 키보드 (기본)
- 조이스틱 (제한적 상황)
- 마이크 (특수 인터랙션)

#### 스마트 디바이스 입력

- 터치 제스처 : 터치 스크린
- 기울기·움직임 : 자이로 센서
- 위치·방위 : GPS 및 네트워크
- 조도·이미지 감지 : 카메라

스마트 디바이스의 다양한 센서를 창의적으로 활용하면 PC에서는 불가능한 고유한 게임 메카닉을 설계할 수 있다.

# 폰트

게임 UI에서 텍스트 가독성은 플레이어 경험의 핵심이다.

## 게임 내 텍스트 표시 방법의 분류

게임에서 텍스트를 화면에 표시하는 방법은 크게 두 가지로 나뉜다. 각 방식은 성능, 표현의 자유도, 유지보수 측면에서 서로 다른 트레이드오프를 가지므로 상황에 맞게 선택해야 한다.

#### 클리어타입 폰트

벡터 기반의 트루타입 폰트 기술을 사용한다. 해상도 유연성이 높지만 프로그램 부하가 상대적으로 크다.

#### 이미지 폰트

완성형 글자 세트를 하나의 이미지로 구성한다. 표현의 자유도는 높지만 해상도 유연성이 낮다

*(이미지 생략: 클리어타입/이미지 폰트 비교 이미지)*

## 클리어타입 폰트

클리어타입 폰트는 벡터 방식의 트루타입(TrueType) 폰트 기술을 기반으로 한다. 다양한 해상도에서 선명한 텍스트를 렌더링할 수 있어 현대 게임에서 널리 사용된다.

**장점**
- 안티 알리아싱, 해상도 조절 가능
- 다양한 크기에서 선명한 렌더링
- 적은 데이터 용량

**단점**
- 폰트 사용 시 라이선스 문제 해결 필수
- 벡터 처리로 인해 프로그램 부하가 상대적으로 큼
- 커스텀 디자인 폰트 적용에 제약

> 상업용 게임에 폰트를 사용할 때는 반드시 상업적 이용 가능한 라이선스 여부를 확인해야 한다. 무료 폰트라도 상업 이용 시 별도 라이선스가 필요한 경우가 많다.

## 이미지 폰트 (비트맵 / 픽셀 폰트)

이미지 폰트는 완성형 글자 세트들을 하나의 이미지(스프라이트 시트) 안에 늘어놓고, 필요한 글자를 잘라 표시하는 방식이다. 게임만의 독특한 텍스트 비주얼을 구현하는데 유리하다.

**장점**
- 폰트 디자인을 자유롭게 커스터마이징 가능
- CPU 렌더링 부하가 클리어타입보다 낮음
- 픽셀 폰트 : 매우 작은 크기에서도 높은 가독성

**단점**
- 해상도 등 서비스 환경에 유동적이지 못함
- 많은 글자 표현 시 메모리 부하 발생
- 다국어 지원 시 글자 수 증가로 리소스 부담 큼

## 이미지 폰트 활용 예

아래는 게임에서 이미지 폰트를 활용한 실제 사례이다. 숫자, 아이콘, 특수문자를 하나의 스프라이트 시트로 구성하여 게임의 아트 스타일과 일체감 있는 텍스트 표현을 구현한 것을 확인할 수 있다.

## 세리프와 산세리프

폰트의 형태는 세리프와 산세리프로 나뉘며, 각각의 특성에 따라 사용 맥락이 다르다. 게임 UI에서는 용도에 맞는 폰트 선택이 가독성에 직접적인 영향을 미친다.

#### 세리프 (Serif)

글자 획의 일부 끝이 돌출된 형태. **가독성(많은 양의 텍스트를 연속으로 읽음)**이 좋아 인쇄물 및 긴 본문 텍스트에 주로 사용된다.

#### 산세리프 (Sans-serif)

획의 굵기가 일정하고 장식이 없는 폰트. **판독성(개별 글자의 형태 식별)**이 좋아 화면 UI 및 짧은 레이블에 주로 사용된다.

*(이미지 생략: 세리프/산세리프 비교 이미지)*

## 폰트 사용 가이드라인

게임 UI에서의 폰트 선택과 활용은 플레이어의 가독성과 게임 전반의 아트 디렉션에 직접적인 영향을 미친다. 아래 가이드라인을 기획 단계부터 적용하면 완성도 높은 UI를 만들 수 있다.

#### 크기에 따른 폰트 선택

폰트 크기가 작아질수록 픽셀 폰트의 가독성이 더 높다. 작은 텍스트에는 이미지 폰트 사용을 검토한다.

#### 디스플레이 환경 최적화

화면 상에서는 세리프체보다 **산세리프체의 가독성이 더 높다.** 상하 몸체를 많이 벗어나는 서체는 UI 설계가 복잡해진다.

#### 폰트 수 제한

한 화면에서 사용하는 폰트는 **2개 이하**가 바람직하다. 폰트 혼용은 시각적 혼란을 유발한다.

#### 다국어 & 색상 고려

다국어 버전의 경우 **UTF-8 규격** 문자셋을 지원하는 폰트를 사용한다. 게임 전반의 색감을 고려해 폰트 색상과 텍스트 박스의 색상을 결정한다.

## UTF-8 타입

유니코드 : 예전 컴퓨터는 영어와 몇가지 특수문자만 사용. 이를 위해서는 1바이트면 충분. 컴퓨터가 보급되고 다른 국가에서도 컴퓨터를 사용하다보니 자국의 문자를 표현하려고 1바이트 안에 임의대로 알파벳 대신 자기나라 글자를 할당하여 그럭저럭 쓸 수 있었지만, 인터넷 시대가 되어 다른 국가의 홈페이지도 들어가보니 글자가 모두 깨짐. 그래서 국제적으로 전세계 언어를 모두 표시할 수 있는 표준 코드를 만들기로 하여 탄생한 것.

유니코드는 아스키 코드와 동일하게 코드표가 정의되어 있다. 남은 것은 이 코드를 컴퓨터에 어떻게 저장해야 되는가? 다른 말로 인코딩. 컴퓨터가 이해할 수 있는 형태로 바꿔주는 것. 예를 들어 가는 0001, 나는 0010이라면 가나나가 → 0001 0010 0010 0001로 저장될 수도 있고 0001001000100001로 저장될 수도 있음. 이렇게되면 각 컴퓨터마다 표시되는 경우가 있고 안되는 경우가 있어 약속을 정함. 이것이 UTF-8이다. *UTF-8은 유니코드를 인코딩하는 방식*. 전세계에서 사용하는 약속이다.
