# UX 디자인

사용자 경험을 설계한다는 것은 무엇을 의미하는가?

## UI의 범주

UI는 HUD만이 아니라 **입출력에 관련된 모든 사용자 인터페이스**를 뜻하며, 게임 UI는 크게 네 가지 범주로 나뉜다.

#### HUD (Heads-Up Display)

체력바, 미니맵, 쿨다운처럼 화면에 상시 표시되는 정보이다. 전투 중에도 필요한 핵심 상태를 즉시 파악하게 해준다.

#### 조작 방식 (Input Interface)

키보드, 마우스, 터치, 조이스틱 등 플레이어의 입력 수단이다. 플랫폼에 맞게 직관적으로 설계해야 한다.

#### 시각적 피드백 (Visual Feedback)

데미지 수치, 아이콘, 이펙트처럼 행동 결과를 바로 보여주는 요소이다. 반응이 명확할수록 타격감과 조작감이 좋아진다.

#### 청각적 피드백 (Audio Feedback)

버튼음, 알림음, 상태 변화 효과음처럼 소리로 전달되는 정보이다. 시각 정보를 보완해 중요한 변화를 빠르게 알려준다.

## UX(User Experience)란?

> 타겟 사용자가 실제로 겪게 되는 체험 - 제품, 시스템, 서비스를 사용하거나 예상하는 사용법에 대한 사람들의 인식과 반응

UX는 단순히 화면 디자인이 아니라, **사용자가 시스템을 통해 느끼는 모든 감정과 경험의 총합**이다.

## UX → UI 설정 단계

좋은 UI는 즉흥적으로 만들어지지 않는다. UX 설계 과정을 거쳐 체계적으로 도출된다.

1. **리서치 : 타겟 유저에 관한 각종 정보 수집**
   경쟁 게임 분석, 유저 인터뷰, 플레이 데이터, 리뷰 분석 등을 통해 유저가 무엇을 원하고 무엇에 불편함을 느끼는지 파악한다.
   예: "왜 튜토리얼에서 이탈률이 높은가?", "어떤 UI 요소가 결제를 방해하는가?"
2. **모델링 : 페르소나, 유저 스토리를 통한 타겟 유저 명확화**
   수집한 데이터를 바탕으로 대표 유저 유형(페르소나)을 정의하고, 그 유저가 게임 내에서 어떤 흐름으로 행동하는지 유저 스토리로 시각화한다.
   예 : "20대 캐주얼 게이머 A는 출퇴근 중 5분 단위로 플레이하며, 복잡한 메뉴는 싫어한다."
3. **전략 디자인 : 타겟 유저에 대한 사용자 체험 전달 전략 수립**
   페르소나를 기반으로 어떤 정보를 어디에 배치할지, 어떤 흐름으로 유저를 유도할지 설계한다. 정보 구조(IA) 화면 흐름도(Flow Chart), 와이어프레임 초안이 이 단계에서 나온다.
   예 : 상점 진입 경로를 3단계에서 1단계로 줄이는 전략 수립
4. **UI 프로토타이핑 : 각종 프로토타이핑 방식을 통한 UI 제작**
   종이 스케치(Lo-fi)부터 figma 기반 인터랙티브 프로토타입(Hi-fi)까지 단계적으로 제작하고, 실제 유저에게 테스트하여 문제점을 발견한다.
   테스트 결과는 다시 리서치 단계로 피드백되어 사이클이 반복된다.

> 각 단계는 순환적으로 연결되며, 특히 프로토타이핑 이후 다시 리서치와 분석으로 돌아오는 반복 과정이 핵심이다.

## UX의 고려 요소

피터 모빌(Peter Morville)의 UX허니콤 모델 - 좋은 UX는 7가지 차원을 균형있게 충족해야 한다. 어느 하나라도 결여되면 전체 경험의 질이 떨어진다.

#### 융통성 (Useful) : 사용자의 필요를 충족하는가

게임에서 제공하는 기능이 플레이어가 실제로 원하는 것인가? 아무리 화려한 UI라도 플레이어가 필요로 하지 않는 기능을 담고 있다면 의미가 없다.
예 : 전투 중 필요없는 정보를 HUD에 가득 채우는 것은 유용하지 않음

#### 사용성 (Usable) : 직관적으로 사용할 수 있는가

처음 접하는 유저도 별도의 설명 없이 UI를 탐색하고 원하는 행동을 수행할 수 있어야 한다. 학습 비용이 낮을수록 이탈률이 줄어든다.
예 : 상점 버튼의 위치가 매번 달라지면 사용성이 떨어진다.

#### 매력성 (Desirable) : 사용하고 싶은가

시각적 완성도, 애니메이션, 색감 등이 유저의 감성을 자극해야 한다. 기능이 같아도 더 예쁜 UI가 더 많이 사용된다.
예 : 레벨업 연출이 화려할수록 성취감과 재방문율이 높아짐

#### 발견성 (Findable) : 쉽게 찾을 수 있는가?

유저가 원하는 기능이나 정보를 빠르게 찾을 수 있도록 정보 구조(IA)가 잘 설계되어야 한다.
예 : 인벤토리→장비→강화 경로가 3번 이상 탭을 거쳐야 한다면 발견성이 낮음

#### 접근성(Accessible) : 누구나 이용 가능한가

색맹, 저시력, 고령 유저 등 다양한 신체적 조건을 가진 플레이어도 불편 없이 사용할 수 있어야 한다.
예 : 색상만으로 상태를 구분하면 색맹 유저는 정보를 파악할 수 없음 → 아이콘·텍스트 병행 필요

#### 신뢰성 (Credible) : 시스템을 믿을 수 있는가?

결제, 아이템 획득, 확률 등 민감한 정보가 명확하게 표시되어야 유저가 게임을 신뢰한다. 불투명한 UI는 불신과 이탈로 이어진다.
예 : 가챠 확률을 숨기거나 결제 금액을 모호하게 표시하면 신뢰도 하락

#### 가치성 (Valuable) : 사용자와 비즈니스 모두에 가치를 제공하는가

유저에게는 즐거운 경험을, 개발사에게는 수익과 지속 가능성을 동시에 제공해야 한다. 어느 한쪽만 이득을 보는 구조는 장기적으로 유지되지 않는다.
예 : 강제 광고 UI는 단기 수익은 높지만 유저 이탈을 유발해 장기적 가치를 훼손

## 페르소나

페르소나란 **해당 프로젝트에 가장 적합한 가상의 타겟 유저**를 말한다. 실제 유저 데이터와 리서치를 바탕으로 만들어지며, 페르소나를 설정함으로써 UI 설계의 방향과 우선순위를 명확히 할 수 있다.

- 프로젝트의 필요에 따라 페르소나의 속성을 맞춤 설정
  - 모바일 RPG라면 "출퇴근 중 플레이하는 직장인", 하드코어 PC 게임이라면 "주말 장시간 플레이어" 등 장르와 플랫폼에 맞는 유저 유형을 정의한다.
- 나이, 직업, 플레이 습관, 소비 성향 등 구체적인 특성 부여
  - 예시 페르소나 : "김지수, 28세, 직장인. 하루 평균 30분 모바일 게임. 월 1~2만원 소비. 복잡한 UI를 싫어하고, 빠른 보상 사이클을 선호."
  - 특성이 구체적일수록 UI 설계 결정이 명확해진다.
- 페르소나로부터 사용자 스토리와 시나리오를 도출
  - "김지수는 점심시간 10분 동안 게임을 켜서 일일 퀘스트를 완료하고 싶다. 그런데 메뉴가 복잡해서 퀘스트 버튼을 찾는데만 2분이 걸린다."
  - 이런 시나리오가 UI 개선의 구체적인 목표가 된다.
- 페르소나는 팀 전체의 공통 언어가 된다.
  - 기획자, 디자이너, 개발자가 "김지수라면 이 UI를 어떻게 느낄까?"라는 공통 기준으로 소통할 수 있어 협업 효율이 높아진다.

> 페르소나는 유저 분석, 목표 수립, 기대 효과 예상 등 마케팅 분야에서도 광범위하게 활용된다. 게임 업계에서는 특히 신규 유저 온보딩 설계와 결제 유도 전략 수립에 핵심적으로 사용된다.

## 좋은 디자인이란?

도널드 노먼은 <The Design of Everyday Things>에서 좋은 디자인을 6가지 원칙으로 설명했으며, 게임 UI에도 그대로 적용된다.

#### 가시성 (Visibility)

**눈에 보이는가?** 사용 가능한 기능과 현재 상태가 명확히 드러나야 한다.

#### 피드백 (Feedback)

**지금 어떤 상태인가?** 모든 행동에는 즉각적인 반응이 있어야 한다.

#### 행위 유도 (Affordance)

**무엇에 쓰는 물건인가?** 디자인 자체가 사용 방법을 자연스럽게 암시해야 한다.

#### 맵핑 (Mapping)

**컨트롤과 실제 효과가 대응되는가?** 조작과 결과의 관계는 직관적이고 논리적이어야 한다.

#### 제약 (Constraint)

**할 수 있는 행동과 할 수 없는 행동의 지정.** 잘못된 행동을 미리 막아 실수를 줄인다.

#### 일관성 (Consistency)

**친숙하고 예측 가능한가?** 같은 기능은 항상 같은 방식으로 표현되어야 한다.

### 좋은 디자인 | 가시성

가시성(Visibility)이란 **사용자가 현재 어떤 상태인지, 어떤 행위가 가능한지를 화면만 보고도 즉시 파악할 수 있어야 한다는 원칙**이다. 숨겨진 기능은 존재하지 않는 것과 같다.

#### 디바이스 상태 인지

현재 가능한 액션을 사용자가 파악할 수 있어야 한다.
어떤 버튼이 활성화되어 있고, 어떤 기능이 지금 사용 가능한지 시각적으로 명확해야 한다.
**게임 예시**: 스킬 버튼이 쿨다운 중일 때 회색으로 어두워지고 타이머가 표시됨. / 인벤토리가 가득 찼을 때 아이템 획득 버튼이 비활성화됨.

#### 정보의 우선순위

중요한 정보와 그렇지 않은 정보를 시각적으로 구분
모든 정보를 동일한 크기와 색상으로 표시하면 유저는 무엇이 중요한지 알 수 없다. 크기, 색상, 위치로 위계를 만들어야 한다.
**게임 예시**: 체력바는 화면 중앙 하단에 크게, 보조 스탯은 작게 / 긴급 알림은 빨간색으로 강조

#### 상황별 정보 은닉

필요하지 않은 상황에서는 정보를 숨겨 혼잡함 방지
항상 모든 정보를 표시하면 화면이 복잡해져 오히려 중요한 정보를 놓치게 된다. 상황에 따라 필요한 정보만 노출하는 것이 좋다.
**게임 예시**: 전투 중에는 전투 관련 UI만 표시. 상점 진입 시 전투 UI 숨김. / 튜토리얼 중 불필요한 메뉴 버튼 비노출

### 좋은 디자인 | 피드백

피드백 (Feedback)이란 유저의 모든 행동에 즉각적이고 명확한 반응이 있어야 한다는 원칙이다. 피드백이 없으면 사용자는 자신의 행동이 시스템에 인식되었는지 알 수 없어 혼란과 불안을 느낀다.

#### 청각적 피드백

효과음은 시각 피드백을 보완하며, 화면을 보지 않아도 상태를 인지할 수 있게 한다.
시선을 UI에 고정하지 않아도 게임 상태를 전달할 수 있어 몰입감을 높인다.
게임 예시 : 스킬 사용 가능 알림음 / 레벨업 팡파레 / 잔액 부족 경고음 / 아이템 획득 효과음

#### 시각적 피드백

버튼 클릭 시 눌리는 애니메이션, 데미지 숫자 팝업, 아이템 획득 시 반짝임 효과 등
화면에서 바로 보이는 변화는 유저가 행동 결과를 가장 빠르게 인지하게 해준다.
게임 예시 : 공격 성공 시 빨간 숫자 팝업 / 크리티컬 히트 시 더 크고 화려한 숫자 / 버튼 hover 시 색상 변화

#### 진동 피드백 (햅틱)

모바일 게임에서 특히 중요하며, 물리적 감각으로 행동의 결과를 전달한다.
손끝으로 느껴지는 반응은 타격감과 조작감을 강화해 작은 행동에도 확실한 응답을 준다.
게임 예시 : 보스 공격 피격 시 강한 진동 / 버튼 탭 시 짧은 진동 / 결제 완료 시 성공 패턴 진동

### 좋은 디자인 | 행위 유도

행위 유도(Affordance)란 디자인의 외형 자체가 사용 방법을 암시해야 한다는 원칙이다. 사용 설명서 없이도 '어떻게 쓰는지'가 직관적으로 느껴져야 하며, 유저가 처음 보는 UI 요소도 자연스럽게 조작할 수 있어야 한다.

#### 모양 (Shape)

디자인의 형태 자체가 사용 방법을 전달한다.
가위는 손가락을 넣어야 한다는 것을 형태로 전달하듯, 볼록하게 튀어나온 버튼은 눌러야 한다는 것을, 슬라이더의 손잡이는 드래그해야 한다는 것을 직관적으로 알려준다.
게임 예시 : 인벤토리 아이템 슬롯의 테두리 → 드래그 가능함을 암시 / 둥근 버튼 → 탭·클릭 유도

#### 텍스트 (Text)

버튼 위의 레이블이 기능을 명확히 설명한다.
아이콘만으로 기능을 전달하기 어려울 때 텍스트 레이블이 보완 역할을 한다. 특히 신규 유저에게는 텍스트가 있는 버튼이 아이콘만 있는 버튼보다 학습 속도를 크게 높인다.
게임 예시 : "강화하기" 버튼 / "상점" 탭 레이블 / "확인·취소" 텍스트 병기

#### 툴팁 (tooltip)

마우스 오버 또는 길게 누르기 시 보충 설명을 제공한다.
아이콘이나 약어만으로는 기능을 파악하기 어려운 경우, 툴팁이 추가 맥락을 제공해 유저의 혼란을 방지한다. 특히 복잡한 스탯이나 스킬 설명에 효과적이다.
게임 예시 : 스킬 아이콘 hover 시 스킬 설명·쿨다운·데미지 수치 표시 / 아이템 아이콘 hover 시 상세 스탯 팝업

### 좋은 디자인 | 맵핑

맵핑(Mapping)이란 컨트롤(조작)과 그 결과(효과) 사이의 관계가 논리적이고 직관적으로 연결되어야 한다는 원칙이다. 위치, 크기, 배치 순서 등이 실제 효과와 **논리적으로 연결**될수록 유저는 별도의 학습 없이 UI를 자연스럽게 사용할 수 있다.

#### 공간적 맵핑 (Spatial Mapping)

컨트롤의 물리적 위치가 결과의 위치와 일치해야 한다
왼쪽 버튼은 왼쪽 효과를, 위쪽 버튼은 위쪽 효과를 내야 유저가 직관적으로 조작할 수 있다.
**게임 예시**: 미니맵에서 왼쪽 클릭 시 캐릭터가 왼쪽으로 이동 / 화면 상단의 볼륨 슬라이더를 오른쪽으로 밀면 소리가 커짐

#### 순서적 맵핑 (Sequential Mapping)

컨트롤의 배치 순서가 실제 작동 순서와 일치해야 한다.
1번 → 2번 → 3번 순서로 진행되는 프로세스라면 버튼도 같은 순서로 배치되어야 혼란이 없다.
**게임 예시**: 장비 강화 UI에서 "재료 선택 → 강화 → 확인" 버튼이 왼쪽에서 오른쪽으로 순서대로 배치

#### 개념적 맵핑 (Conceptual Mapping)

유저가 이미 알고 있는 개념과 일치하는 방식으로 설계해야 한다.
현실 세계에서 익숙한 패턴(위 = 증가, 빨강 = 위험, 자물쇠 = 잠금)을 UI에 그대로 적용하면 학습 비용이 줄어든다.
**게임 예시**: 체력바가 줄어들수록 빨간색으로 변함 / 잠긴 콘텐츠에 자물쇠 아이콘 표시 / 레벨이 높을수록 아이콘이 위에 배치

### 좋은 디자인 | 제약

제약(Constraint)이란 사용자가 잘못된 행동을 하지 못하도록 구조적으로 막아 실수를 방지하는 원칙이다. 토스터는 빵 이외의 물건을 넣기 어렵게 설계되어 있듯, 좋은 UI는 유저가 실수할 수 있는 경로 자체를 차단한다.

#### 물리적 제약 (Physical Constraint)

형태나 구조 자체가 잘못된 사용을 막는다.
USB 포트는 방향이 맞지 않으면 꽂히지 않고, 토스터 슬롯은 빵 크기에 맞게 설계되어 있다.
**게임 예시**: 모바일 게임의 가상 조이스틱은 화면 밖으로 드래그 되지 않음 / 인벤토리 슬롯은 해당 타입의 아이템만 장착 가능

#### 논리적 제약 (Logical Constraint)

현재 상황에서 불가능한 행동을 시각적으로 비활성화한다.
조건이 충족되지 않은 버튼은 회색으로 비활성화하여 클릭 자체를 막거나, 클릭 시 이유를 안내한다.
**게임 예시**: 레벨 미달 장비의 장착 버튼 비활성화. 재화 부족 시 구매 버튼 잠금 + "골드가 부족합니다" 안내

#### 의미적 제약 (Semantic Constraint)

상황의 의미와 맥락이 행동을 자연스럽게 제한한다.
삭제·결제처럼 되돌리기 어려운 행동 전에는 확인 팝업을 띄워 실수를 방지한다.
**게임 예시**: 아이템 영구 삭제 전 "정말 삭제하시겠습니까" 확인창 / 결제 완료 전 최종 확인 단계 추가

### 좋은 디자인 | 일관성

일관성(Consistency)이란 비슷한 기능을 수행하는 요소는 항상 비슷한 방식으로 표현되어야 한다는 원칙이다. 유저가 한 번 학습한 패턴이 게임 전체에 걸쳐 동일하게 적용될수록, 새로운 화면에서도 별도의 학습없이 자연스럽게 적응할 수 있다.

#### 내부 일관성 (Internal Consistency)

같은 게임 내에서 동일한 규칙이 반복 적용되어야 한다.
닫기 버튼은 항상 우측 상단, 확인은 파란색, 취소는 회색, 중요 알림은 빨간색 등 게임 내 모든 화면에서 동일한 패턴을 유지해야 한다.
**게임 예시**: 모든 팝업창의 닫기 버튼 위치 동일 / 모든 탭 메뉴의 선택 상태 표시 방식 통일

#### 외부 일관성 (External Consistency)

유저가 다른 게임이나 앱에서 이미 학습한 패턴을 그대로 활용할 수 있어야 한다.
업계 표준 UI 패턴을 따르면 신규 유저의 학습 비용이 크게 줄어든다.
**게임 예시**: 인벤토리는 가방 아이콘, 설정은 톱니바퀴 아이콘 / 스와이프로 화면 전환 / 좌측 상단 뒤로가기 버튼

#### 시각적 일관성 (Visual Consistency)

색상, 폰트, 아이콘 스타일, 버튼 크기 등 시각 요소가 전체 게임에서 통일된 디자인 시스템을 따라야 한다.
화면마다 버튼 색상이나 폰트가 달라지면 유저는 혼란을 느끼고 게임의 완성도가 낮아 보인다.
**게임 예시**: 주요 액션 버튼은 항상 골드 색상 / 경고 메시지는 항상 빨간 테두리 / 아이콘은 동일한 선 굵기와 스타일 유지

# UI 설계하기

사용성(Usability)을 중심으로 UI를 체계적으로 구성하는 방법

## Usability - 사용성

> UI의 핵심 가치. **보다 사용하기 편리한 시스템을 만들기 위한 설계와 평가 과정** 전체를 의미한다.

Usability는 단순히 "쓰기 편한 것"을 넘어, 사용자가 목표를 얼마나 효율적·효과적·만족스럽게 달성하는지를 측정하는 기준이다. ISO 9241은 이를 효과성(Effectiveness), 효율성(Efficiency), 만족도(Satisfaction)의 세 축으로 정의한다.

#### 효과성 (Effectiveness)

유저가 목표를 정확하게 달성할 수 있는가?
오류 없이 원하는 기능을 수행할 수 있는지를 측정한다. 목표 달성 성공률, 오류 발생 횟수 등으로 정량화할 수 있다.
**게임 예시**: 튜토리얼 완료율 / 상점에서 원하는 아이템을 3번 이내 탭으로 구매 가능한지 여부

#### 효율성 (Efficiency)

목표를 달성하는 데 얼마나 적은 시간과 노력이 드는가?
과제 완료 시간, 클릭 수, 화면 이동 횟수 등으로 측정한다. 같은 목표라도 더 빠르고 적은 조작으로 달성할수록 효율성이 높다.
**게임 예시**: 일일 퀘스트 수령까지 걸리는 탭 수 / 인벤토리 정렬에 소요되는 시간

#### 만족도 (Satisfaction)

사용 경험 자체가 즐겁고 긍정적인가?
기능이 완벽해도 사용하는 과정이 불쾌하면 유저는 이탈한다. 설문, 리뷰, 재방문율 등으로 측정한다.
**게임 예시**: "이 UI 쓰기 편해요" 리뷰 비율 / 상점 방문 후 구매 전환율 / 게임 내 설정 화면 재방문율

## Usability의 핵심 항목들

Jakob Nielsen이 정의한 Usability의 5가지 핵심 항목이다. 이 항목들은 서로 독립적이지 않으며, 특히 학습의 용이성과 사용의 편의성은 상충 관계에 있어 균형 설계가 필요하다.

#### 학습의 용이성 (Learnability) : 처음 사용하는 유저가 얼마나 빠르게 시스템을 익힐 수 있는가?

아이콘, 툴팁, 튜토리얼 등 시각적 단서를 활용해 학습 비용을 낮춘다. 신규 유저가 첫 10분 안에 핵심 기능을 파악할 수 있어야 한다.
**게임 예시**: 첫 접속 시 핵심 버튼에 화살표 가이드 표시 / 스킬 아이콘에 기능명 툴팁 제공

#### 사용의 편의성 (Efficiency) : 익숙해진 유저가 얼마나 빠르고 적은 조작으로 목표를 달성할 수 있는가?

숙련자를 위한 단축키, 즐겨찾기, 퀵슬롯 등 고급 경로를 제공해 반복 작업의 효율을 높인다.
**게임 예시**: 자주 쓰는 아이템을 퀵슬롯에 등록 / 일일 퀘스트 바로가기 버튼 / 인벤토리 자동 정렬

#### 기억의 용이성 (Memorability) : 오랜만에 다시 사용해도 금방 다시 익힐 수 있는가?

일관된 UI 패턴과 직관적인 아이콘을 사용하면 재학습 비용이 줄어든다. 업데이트 후 UI가 크게 바뀌면 기존 유저도 혼란을 겪는다.
**게임 예시**: 대규모 업데이트 후 주요 버튼 위치 유지 / 아이콘 스타일 일관성 유지

#### 적은 오류 (Error Rate) : 실수를 유발하는 요소가 최소화되어 있는가? 오류 발생 시 쉽게 복구할 수 있는가?

비슷하게 생긴 버튼을 인접 배치하거나, 되돌리기 어려운 행동에 확인 단계가 없으면 오류율이 높아진다.
**게임 예시**: 삭제·판매 버튼을 획득 버튼과 멀리 배치 / 실수로 아이템 판매 시 일정 시간 내 취소 가능

#### 주관적 즐거움 (Satisfaction) : 사용 자체가 즐겁고 긍정적인 감정을 주는가?

"아름답다, 깔끔하다, 반응이 빠르다"는 느낌은 기능적 완성도와 별개로 유저 만족도와 재방문율에 직접 영향을 미친다.
**게임 예시**: 버튼 클릭 시 경쾌한 효과음 + 애니메이션 / 레벨업 연출의 시각적 화려함 / 로딩 화면의 팁 제공

> 학습의 용이성과 사용의 편의성은 상충된다. 초보자는 아이콘으로, 숙련자는 단축키로 - 다중 경로 시스템을 도입한다.

## UI에서 고려되어야 하는 요소

좋은 UI를 설계하려면 단순히 "예쁜 화면"을 만드는 것을 넘어, 사람·환경·기술 세 가지 측면을 종합적으로 고려해야 한다.

#### 인간의 능력

인지, 지각, 운동 능력 등 사람이 처리할 수 있는 정보량의 한계를 고려한다. 인간은 한 번에 7±2개의 정보만 단기 기억에 저장할 수 있어, 정보를 너무 많이 동시에 보여주면 인지 과부하가 생긴다.

#### 사용자 계층 특성

연령, 숙련도, 디바이스 친숙도 등 타겟 유저의 다양한 속성을 반영한다. 사용자 특성에 따라 같은 UI도 다르게 경험되므로, 연령과 숙련도에 맞춰 복잡도와 정보 밀도를 조절해야 한다.

#### 사용 환경

같은 기능이라도 상황에 따라 다른 의미와 우선순위를 가진다. 전투 중에는 빠른 반응이 중요하고 설정 화면에서는 정확성이 중요하므로, 상황에 맞게 배치와 크기를 다르게 설계해야 한다.

#### 선행·필요 조건

특정 기능을 사용하기 위한 조건이 있다면 명확하게 전달해야 한다. 조건이 충족되지 않았을 때는 비활성화만 하지 말고, 무엇이 필요한지와 왜 불가능한지를 함께 알려야 한다.

#### 디바이스 특성

키보드, 조이스틱, 터치스크린, 진동 피드백 등 입출력 방식의 차이를 반영한다. 플랫폼마다 조작 방식이 다르므로, PC·콘솔·모바일에 맞는 UI와 상호작용 방식을 각각 고려해야 한다.

## UI의 기대 효과 측정 방법

UI의 품질은 **정량적으로 측정**할 수 있다. 아래 지표들을 통해 개선 전후를 객관적으로 비교하고, 어떤 UI가 더 효과적인지 데이터로 증명할 수 있다.

#### 과제 완료 시간

특정 목표를 달성하는 데 걸리는 시간, 화면 이동 횟수, 클릭/탭 수를 측정한다. 수치가 낮을수록 효율적인 UI이다. A/B 테스트를 통해 두 가지 UI 중 어느 쪽이 더 빠른지 비교할 수 있다.

#### 오류 지표

잘못 선택한 횟수, 반복된 에러 발생 횟수, 에러 발생 후 복귀까지 걸린 시간을 측정한다. 오류율이 높은 UI 요소는 위치·크기·레이블을 재검토해야 한다. 특히 되돌리기 어려운 행동(삭제, 결제)에서의 오류는 유저 이탈로 직결된다.

#### 외부 도움 빈도

다른 유저, 헬프데스크, 공식 가이드, 커뮤니티 등 UI 외부에 도움을 요청한 빈도를 측정한다. "이거 어떻게 하는 거야?"라는 질문이 많이 올라오는 기능은 UI가 직관적이지 않다는 신호이다. 커뮤니티 질문 빈도나 고객센터 문의량이 간접 지표가 된다.

#### 도움 접근성

유저가 막혔을 때 도움말이나 가이드에 얼마나 쉽고 빠르게 접근할 수 있는지를 측정한다. 도움말이 있어도 찾기 어려우면 없는 것과 같다. 도움말 버튼 클릭률, 튜토리얼 완료율, FAQ 페이지 이탈률 등으로 측정한다.

## 사용자 측면의 분석

UI를 설계하기 전, 사용자를 네 가지 관점에서 분석해야 한다. 사용자가 무엇을 원하고, 어떻게 행동하며, 어떤 상황에서 사용하는지를 파악해야 진짜 문제를 해결하는 UI를 만들 수 있다.

#### 컨텐츠 가치 분석

이 기능이 유저에게 꼭 필요한가? 컨텐츠에 대해 느끼는 가치는 사람마다 다르다. 같은 강화 시스템이라도 하드코어 유저에게는 핵심 콘텐츠지만, 캐주얼 유저에게는 복잡하고 불필요한 기능으로 느껴질 수 있다. UI에 담기 전에 "이게 정말 필요한가?"를 먼저 검증해야 한다.

#### 사용자 분석

사용자가 중요하게 느끼는 가치는 무엇인가? (기능성, 유희성, 개성) 숙련도는 어느 수준인가? 기능성을 중시하는 유저는 정보 밀도가 높은 UI를 선호하고, 유희성을 중시하는 유저는 화려한 연출과 보상 피드백을 선호한다. 개성을 중시하는 유저는 커스터마이징 옵션을 원한다.

#### 과업 분석

유저가 실제로 어떤 방식으로 시스템을 사용하는가? 설계 의도와 다른 사용 패턴은 없는가? 유저는 종종 개발자가 의도하지 않은 방식으로 UI를 사용한다. 이런 패턴을 발견하면 UI를 개선하거나 새로운 기능으로 공식화할 수 있다.

#### 상황 분석

어떤 상황에서, 어떤 맥락으로 이 UI를 사용하는가? 같은 아이템이라도 전투 중 긴급하게 사용하는 상황과 인벤토리를 정리하는 여유로운 상황은 완전히 다른 UI 설계를 요구한다.

## 기술적 측면의 분석

아무리 훌륭한 UX 설계도 기술적 한계를 고려하지 않으면 구현이 불가능하다. UI 설계자는 개발 환경과 플랫폼의 기술적 특성을 이해하고, 실현 가능한 범위 안에서 최선의 설계를 해야 한다.

#### 구현 가능한 수준

현재 팀의 기술력, 개발 일정, 사용 중인 엔진·프레임워크 안에서 실현 가능한 범위를 파악한다.
아무리 멋진 UI 애니메이션이라도 팀의 기술 스택이나 일정이 뒷받침되지 않으면 구현할 수 없다. 설계 단계에서 개발자와 긴밀히 소통해 실현 가능성을 검증해야 한다.

#### 디스플레이 특성

화면 크기, 해상도, 픽셀 밀도(PPI), 화면 비율 등 플랫폼별 디스플레이 차이를 반영한다.
모바일은 작은 화면에 고밀도 픽셀, PC는 큰 화면에 다양한 해상도, 콘솔은 TV 거실 시청 거리를 고려해야 한다. 하나의 UI가 모든 환경에서 동일하게 보이지 않는다.

#### 입력 장치

키보드, 마우스, 조이스틱, 터치스크린, 모션 컨트롤러 등 플랫폼별 입력 방식의 차이를 반영한다.
마우스는 정밀한 포인팅이 가능하지만 터치는 손가락 굵기만큼의 오차가 생긴다. 조이스틱은 포커스 이동 방식으로 UI를 탐색하므로 탭 순서 설계가 중요하다.

#### 속도 (Performance)

렌더링 성능, 네트워크 지연, 로딩 시간 등이 UI 반응 속도와 체감 품질에 직결된다.
버튼을 눌렀을 때 100ms 이내에 반응이 없으면 유저는 "눌렀나?"라고 느끼고 다시 탭한다. 네트워크 지연이 있는 경우 로딩 인디케이터로 대기 상태를 명확히 표시해야 한다.

## UI와 다른 파트 개발과의 차이

> UI 개발은 **분석 → 구현 → 평가의 반복 사이클**로 이루어지며, 수시로 기획 수정과 추가가 필요하다. 일반 게임 로직 개발과 달리 UI는 '완성'이 없다 - 유저 피드백에 따라 끊임없이 개선된다.

#### 분석

사업 목적과 사용자 목적 달성을 위한 Usability Goal을 설정하고 분석한다.
일반 게임 기능 개발은 "이 기능을 구현한다"는 명확한 목표가 있지만, UI는 "이 기능을 유저가 얼마나 쉽게 사용할 수 있는가"라는 상대적 목표를 다룬다. 따라서 분석 단계에서 측정 가능한 목표(KPI)를 먼저 설정해야 한다.

#### 구현

디자인 → 테스트 → 개발의 순서로 진행되며, 각 단계가 긴밀하게 연결된다.
일반 개발은 기획 → 개발 → QA의 선형 흐름이지만, UI는 와이어프레임 → 프로토타입 → 유저 테스트 → 수정 → 개발의 반복 구조이다. 개발 전에 프로토타입으로 검증하는 것이 핵심이다.

#### 평가

테스트, 인터뷰, 설문지 등 다양한 방법으로 유저 피드백을 수집한다.

UI 평가는 QA(버그 수정)와 다르다. 기능이 정상 작동해도 유저가 불편하면 실패한 UI이다. 정량적 지표(완료 시간, 오류율)와 정성적 피드백(인터뷰, 설문)을 함께 활용해야 한다.

> 중요도와 예상 완료 시점에 따라 **유동적으로 스케줄링**하는 것이 핵심이다.

### 가시성

가시성(Visibility of System Status)이란 시스템이 현재 어떤 상태인지를 유저에게 항상 명확하게 알려줘야 한다는 원칙이다. 유저가 "지금 내 행동이 반영됐나?", "로딩 중인가, 멈춘건가?" 라고 의심하는 순간, 신뢰는 무너진다. 특히 게임 UI에서는 선택 상태, 사용 가능 여부, 처리 중 상태가 즉시 드러나야 반복 클릭과 혼란을 줄일 수 있다.

### 현실 세계와의 부합

현실 세계와의 부합(Match Between System and Real World)이란 시스템이 내부 논리가 아니라 유저가 일상에서 쓰는 언어, 개념, 관습을 따라야 한다는 원칙이다. 유저는 새로운 언어를 배우러 게임을 하는 것이 아니다. UI가 현실과 동떨어진 용어나 구조를 사용하면 유저는 매번 "이게 무슨 뜻이지?" 하고 해석해야 하고, 그 인지 부하가 쌓이면 결국 이탈로 이어진다.

#### 실세상과의 부합

실생활에서 늘 사용하는 용어를 사용하는가? 아이콘이 실제 세상과 비슷하게 표현되어 있는가?

#### 상식적 논리와의 부합

계층과 관계별로 구분되어 있는가? 유저가 별도 학습 없이 구조를 파악할 수 있는가?

#### 사용자 과업과의 부합

실제 사용자가 해야 하는 작업과 동일한 이름을 사용하는가? 버튼 명칭이 행동을 명확히 나타내는가?

#### 예상 행위와의 부합

어디를 선택해야 하고 어떤 작업을 하는지가 명확한가? 유저의 기존 행동과 실제 결과가 일치한가?

### 컨트롤

컨트롤(User Control and Freedom)은 유저가 실수했을 때 쉽게 되돌아올 수 있는 '비상구'를 제공하는 원칙이다. 유저는 실수를 할 수 있으므로, 중요한 것은 실수 후 회복이 쉬워야 한다는 점이다. 언제든 돌아오고, 수정하고, 중단할 수 있어야 유저가 안심하고 행동할 수 있다.

#### 전반적인 사용자 주도권

사용자가 원하는 시점에 원하는 행동을 할 수 있어야 한다. 강제로 진행을 제한하거나 특정 행동만 허용하면 주도권이 줄어든다.

#### 취소 가능성

선택한 행동은 쉽게 취소할 수 있어야 하고, 비가역적 행동 전에는 충분한 경고가 필요하다. 되돌릴 수 없는 기능일수록 복구 장치가 중요하다.

#### 사용자의 자유도

유저는 과업을 다양한 방식으로 수행하고, 중간에 경로를 바꾸거나 나갈 수 있어야 한다. 다시 시작하고 돌아갈 수 있다는 확신이 있어야 탐색이 편해진다.

### 일관성

일관성(Consistency and Standards)이란 같은 기능은 언제나 같은 방식으로 표현되어야 한다는 원칙이다. 유저는 한 화면에서 배운 규칙을 다른 화면에서도 그대로 적용하려 한다. 일관성이 깨지면 유저는 매번 새로 학습해야 하고, 이는 곧 인지 부하와 실수로 이어진다.

#### 일관성 있는 이름

메뉴, 명령어, 약자가 일관성있게 제시되는가?

#### 일관성 있는 정보

메뉴, 제목, 에러 메시지 등이 전체적으로 통일되어 있는가?

#### 일관성 있는 구조

확인, 취소, 도움말 등 중요 버튼의 위치가 화면마다 동일한가?

#### 일관성 있는 표현

아이콘, 스타일, 색감, 컨셉의 통일성이 유지되는가?

### 에러 방지

에러 방지(Error Prevention)란 오류 메시지를 잘 만드는 것보다, 오류 자체가 발생하지 않도록 설계하는 것이 더 중요하다는 원칙이다. 유저는 실수를 하기 마련이지만, 좋은 UI는 그 실수가 일어나기 전에 구조적으로 막아준다. 특히 비가역적 행동(영구 삭제, 결제, 강화 실패 등)에서 에러 방지는 유저 신뢰와 직결된다.

#### 오류 확률 낮추기

헷갈리는 문자, 혼동되는 데이터 배치 등을 원천적으로 제거해 사용자의 오조작 가능성을 줄인다.

#### 오류 유발 요소 숨기기

현재 상태에서 실제로 가능한 행동만 화면에 노출하고, 불가능한 행동은 비활성화하거나 숨긴다.

#### 심각한 오류 방지

되돌릴 수 없는 행동에는 결과 경고, 기능 버튼 위치 차별화, 재확인 팝업을 적용해 실수를 차단한다.

#### 예상 결과 미리 보여주기

행동 전에 어떤 결과가 나타날지 시각적으로 미리 보여주어, 선택의 부담과 후회를 줄인다.

### 즉각적 인지

즉각적 인지(Recognition Rather Than Recall)란 유저가 기억에 의존하게 만들지 말고, 필요한 정보를 화면에 직접 보여줘야 한다는 원칙이다. 인간의 단기 기억은 한계가 있어, 이전 화면에서 본 정보를 기억하며 다음 행동을 결정하게 만들면 인지 부하가 급격히 증가한다. "보면 알 수 있는" UI가 "기억해야 하는" UI보다 항상 우월하다.

#### 기억하기 쉬운 구조

작업 순서와 메뉴 항목 배치가 자연스러운 흐름으로 구성되어 있어, 유저가 다음 행동을 외우지 않아도 바로 이어서 진행할 수 있어야 한다.

#### 명확한 명칭과 툴팁

아이콘이나 명령어의 이름을 명확히 제시하고, 필요한 경우 툴팁으로 의미를 보완해 유저가 기능을 기억하지 않아도 되게 만들어야 한다.

#### 적절한 그룹핑

비슷한 기능끼리 논리적으로 묶어 한눈에 파악할 수 있게 구성하면, 유저는 항목의 의미를 일일이 기억하지 않고도 위치와 묶음만으로 이해할 수 있다.

#### 시각적 계층 구조

중요한 정보가 시각적으로 강조되어 있어야 하며, 유저의 시선이 자연스럽게 핵심 정보로 향하도록 크기, 색상, 위치를 조절해야 한다.

### 융통성

융통성(Flexibility and Efficiency of Use)이란 초보 유저와 숙련 유저 모두를 만족시킬 수 있도록 다양한 사용 경로를 제공해야 한다는 원칙이다. 초보자에게는 친절한 안내가, 숙련자에게는 빠른 조작 경로가 필요하다. 하나의 방식만 강요하는 UI는 어느 한쪽 유저를 반드시 불편하게 만든다.

#### 전문성에 따른 유연성

숙달될수록 더 복잡한 명령을 사용할 수 있고, 더 많은 정보를 제공받을 수 있어야한다. 초보자와 숙련자의 정보량과 조작 난이도를 같은 수준으로 고정하면, 한쪽은 과도하게 복잡하고 다른 한쪽은 너무 단순해진다.

#### 다양한 옵션 제공

같은 작업을 여러 가지 방법으로 수행할 수 있어야 하며, 단 하나의 경로만 존재해서는 안된다. 유저마다 익숙한 조작 방식이 다르기 때문에, 선택지가 많을수록 사용 장벽이 낮아진다.

#### 개인화

사용자가 UI를 자신에게 편리하게 재구성할 수 있어야 한다. 단축키, 레이아웃, 정보 표시 방식까지 조정 가능하면 유저는 자신의 습관과 플레이 스타일에 맞게 화면을 최적화할 수 있다.

반복적이고 기계적인 작업을 시스템이 대신 처리해 주어야 한다. 유저가 매번 같은 행동을 직접 반복하지 않아도 되면,

### 비주얼

비주얼(Aesthetic and Minimalist Design)이란 UI에서 꼭 필요한 요소만 남기고 불필요한 정보와 장식을 줄여, 내용을 더 명확하고 보기 좋게 만드는 원칙이다. 요소가 많을수록 중요한 정보가 묻히고 인지 부담이 커지므로, 화면은 단정하고 일관되게 정리되어야 한다.

#### 심미성

색상, 서체, 배치가 조화롭게 정리되어야 하며, 특히 색상 대비가 충분해 가독성이 확보되어야 한다. 서체도 2~3종 이내로 제한하고 그리드에 맞춰 정렬하면 화면이 더 안정적이고 신뢰감 있게 보인다.

#### 최소한의 표현

Less is More 원칙처럼, 색상·폰트·도형·장식은 꼭 필요한 수준만 남겨야 한다. 보통 주조색 1개, 보라색 1~2개, 강조색 1개 정도로 제한하면 시선이 분산되지 않고 핵심 정보가 더 잘 드러난다.

#### 최소한의 입력 요구

사용자에게 불필요한 입력과 반복 작업을 요구하지 않아야 하며, 클릭 수와 화면 전환 수도 가능한 한 줄여야 한다. 자동 완성, 기본값, 기억 기능을 활용하면 조작 단계가 짧아지고 사용자는 목표 행동에 더 빠르게 도달할 수 있다.

### 에러 해결

에러 해결은 오류가 발생했을 때 유저가 상황을 바로 인식하고, 원인을 파악하며, 스스로 복구할 수 있도록 돕는 원칙이다. 오류를 인지하지 못하면 문제를 해결할 출발점 자체가 사라지므로, 안내는 빠르고 분명해야 한다. 또한 오류 메시지는 쉬운 언어로 쓰고, 다음 행동까지 자연스럽게 이어지도록 설계해야 한다.

#### 에러 감지

유저가 에러 발생을 즉시 알아차릴 수 있도록 명확한 피드백을 제공해야 한다. 오류가 보이지 않으면 사용자는 정상 동작으로 오해해 같은 행동을 반복할 수 있으므로, 눈에 잘 띄는 위치와 즉각적인 반응이 중요하다. 색상, 아이콘, 효과음 등을 함께 써서 상황을 분명하게 알려줘야 한다.

#### 에러 원인 진단

오류의 원인을 기술 용어가 아닌 일상 언어로 설명해야 한다.

#### 에러 복구

유저가 바로 시도할 수 있는 해결 방법과 복구 경로를 제시해야 한다. 재시도 버튼, 복구 버튼, 고객센터 연결처럼 즉시 실행 가능한 행동을 제공하는 것이 중요하며,

> 자주 발생하는 에러는 자동 보정 기능으로 더 빠르게 복구할 수 있다. 예를 들어 네트워크 자동 재연결이나 입력 오류 시 유사 값 자동 제안이 대표적이다.

### 보충 설명

보충 설명(Help and Documentation)이란 유저가 시스템을 이해하거나 문제를 해결할 때 필요한 정보를 언제든지 쉽게 찾을 수 있도록 제공해야 한다는 원칙이다. 이상적인 UI는 도움말 없이도 직관적으로 사용할 수 있어야 하지만, 복잡한 기능이 포함된 경우는 도움말은 반드시 갖춰져야 한다. 도움말은 유저가 필요로 하는 순간에 맥락에 맞게 제공되어야 하며, 검색 가능하고 구체적인 단계로 안내해야 한다.

#### 도움말 제공

상황을 빠르게 파악하고, 바로 따라할 수 있어야 한다. 선택 가능한 대안이나 다음 행동도 함께 제시하면 더 좋다.

#### 도움말의 표현

눈에 잘 띄고 이해하기 쉬운 언어로 써야한다. 글과 그림을 적절히 섞어 정보를 쉽게 전달하는 것이 중요하다.

#### 작업 전환의 용이함

원래 작업과 도움말 사이를 자연스럽게 오갈 수 있어야 한다. 도움말을 본 뒤에도 현재 흐름으로 쉽게 돌아갈 수 있어야 한다.
