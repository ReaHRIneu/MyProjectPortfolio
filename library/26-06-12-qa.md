# QA | Quality Assurance

품질 보증(QA)은 소프트웨어 개발의 전 영역에 참여하여 SW의 복합적인 품질 요소에 대한 보장성을 확보하는 일련의 과정이다. 단순 검수를 넘어, 프로세스 전반을 개선하고 팀의 품질 수행 역량을 높이는 역할을 담당한다.

#### 품질 수행 코칭

프로세스 적용 가이드 제공, 팀의 품질 역량 향상을 위한 자문 및 테일러링 가이드 수행

#### 프로세스 품질

개발 프로세스 준수 여부를 Audit하고, 산출물과 절차가 표준에 부합하는지 적합성 체크

#### 프로덕트 품질

테스팅 및 지표 수집을 통해 산출물의 정확성, 적합성, 품질 수준을 직접 평가하고 검증

## 게임 QA의 필요성

#### 일반 제품의 경우

소비자가 구매 후 품질 문제를 인지하더라도, 적극적인 반품 비율은 낮다. 이미 판매가 완료되었기 때문에 단기 매출 손실이 제한적이다. 다음 구매를 포기하더라도 현재 판매분은 유지된다.

#### 게임의 경우

게임은 단번에 구매가 결정되지 않는다. 유저는 플레이 전부터 평가를 형성하며, 낮은 품질 평가는 초기 접속 자체를 막는다. 출시 초반의 부정적 인상은 이후 유저 유입을 영구적으로 저해할 수 있어 QA는 선택이 아닌 필수이다.

## 게임 QA의 기준

게임 QA의 기준은 내부 목표를 기반으로 한 절대적 기준과 경쟁 제품과의 비교를 통한 상대적 기준, 두 가지 축으로 구성되며 이를 균형있게 충족해야 출시 품질을 보장할 수 있다.

#### 절대적 기준 | 내부 목표 기반

- **게임 콘텐츠 수량**: 목표 분량이 충족되었는지 확인한다. 기획 단계에서 정의된 콘텐츠 목록과 실제 구현 수량을 대조하여 누락 여부를 점검한다.
- **타겟층 적합성**: 타겟 유저에 맞는 콘텐츠 구성 여부를 검토한다. 연령대, 장르 선호도, 플레이 패턴 등을 고려해 콘텐츠가 타겟 유저에게 적합한지 검토한다.
- **목표 플레이 시간**: 콘텐츠 소모량 기준 달성 여부를 확인한다. 스테이지 수, 퀘스트 분량, 반복 플레이 요소 등을 종합하여 목표 시간 달성 여부를 산출한다.
- **허용 결함 수위**: 런칭 시 내재할 수 있는 문제의 임계치를 점검한다. 런칭 전 잔존 버그의 심각도와 수량이 사전에 합의된 임계치 이내인지 최종 확인한다.

#### 상대적 기준 | 경쟁 제품 대비

- **게임 내 밸런스**: 경쟁작 대비 동급 이상의 균형감이 필요하다. 캐릭터·아이템·난이도 등 주요 요소가 경쟁작 수준 이상의 균형감을 갖추고 있는지 비교 분석한다.
- **편의성**: UX 흐름과 인터페이스 직관성을 확인한다. 주요 경쟁작의 UX 흐름과 비교하여 불필요한 단계나 혼란을 유발하는 인터페이스 요소를 식별한다.
- **하드웨어 호환성**: 다양한 기기에서의 안정적 동작을 검증한다. 출시 대상 기기 목록을 기준으로 각 환경에서 크래시·렉·해상도 이상 여부를 체계적으로 검증한다.
- **네트워크 성능**: 사용량 및 응답 속도 최적화가 필요하다. 동시 접속 부하 테스트와 응답 속도 측정을 통해 서비스 안정성이 경쟁작 대비 열위하지 않음을 확인한다.

## 게임 QA의 필요 요소

"신뢰를 잃게 되면 QA 활동의 의미가 퇴색된다"

#### 표준화 방안

개발 방법론 및 내부 프로세스 표준화, QA 업무 진행 매뉴얼 정비. 일관된 기준이 없으면 테스터마다 결과가 달라져 품질 판단의 신뢰성이 떨어진다.

#### 시장 분석

제품 분석 및 시장 트렌드 조사, 경쟁사 동향 파악. 시장 흐름을 파악해야 QA 기준을 경쟁력 있는 수준으로 설정할 수 있다.

#### 개발 히스토리

개발 진행 정보, 솔루션, 히스토리 및 향후 목표 공유. 과거 이슈와 해결 방식을 공유함으로써 동일한 문제의 반복을 사전에 방지할 수 있다.

#### 일정 및 리스크

목표 일정, 개발 컨셉, 리소스 현황 및 개발 리스크 파악. 리스크를 조기에 식별하면 테스트 우선순위를 조정하여 한정된 자원을 효율적으로 배분할 수 있다.

## QA 시점

QA는 특정 마일스톤에만 국한되지 않고, 개발 생명주기 전반에 걸쳐 지속적으로 수행된다. 각 시점마다 목적과 범위가 다르며, 이를 명확히 이해하는 것이 효과적인 QA 수행의 출발점이다.

1. **알파 / 클로즈 베타 / FGT**: 특정 개발 단계 도달 시점에 수행하는 집중 테스트
2. **서비스 오픈 전**: 출시 직전 최종 검증 및 Sign-off 판단
3. **서비스 오픈 후**: 라이브 환경에서의 지속적 품질 모니터링
4. **점검 / 장애 복구**: 임시점검 및 정기점검, 장애 발생 후 복구 확인

## 버그 관리

버그는 발견 즉시 등록하고, 담당자 할당 → 수정 → 확인 종료의 명확한 흐름으로 추적 관리한다. 재발견된 버그(Reopen)는 동일한 프로세스를 반복하며, 완전히 해소될 때까지 추적을 이어간다.

#### 결함 등록

BTS에 버그 내용, 재현 방법, 심각도를 기록하여 누락 없이 정확하게 기록해야 개발자가 재현 및 수정에 드는 시간을 최소화할 수 있다.

#### 담당자 할당

우선순위에 따라 개발자에게 수정 의뢰하며, 할당 시 담당자에게 수정기한도 함께 전달하여 일정 내 처리가 이루어지도록 한다

#### 버그 확인/수정

수정 완료 후 QA가 재검증(Retest) 수행하며, 단순 수정 확인에 그치지 않고, 관련 기능에 부작용이 없는지 함께 점검한다.

#### 종료

정상 확인 시 Close, 미해결 시 Reopen 처리하며, Reopen된 버그는 수정 이력과 함께 재등록되어 반복 발생 패턴을 추적하는 데 활용된다.

모든 버그는 BTS(Bug Tracking System)에 등록되어 이력이 관리되며, 팀 전체가 동일한 기준으로 결함 상태를 공유한다.

## 버그로 등록해야 할 항목

버그의 범위는 단순한 오류를 넘어 유저 경험에 영향을 주는 모든 문제를 포함한다. 명세서 기준의 일탈뿐 아니라 UX 관점의 불편함도 버그로 등록되어야 한다.

#### 명세서 미준수 동작

상점에서 여러 아이템을 한 번에 구입해야 하는데 한 개씩만 구매 가능한 경우. 명세서와 실제 동작의 불일치는 가장 기본적인 버그 유형으로, 기획 의도가 구현에 정확히 반영되었는지를 확인하는 것이 핵심이다.

#### 명세서 외 동작 수행

전설급 아이템이 상점에 판매되어서는 안 되는데 실제로 판매되고 있는 경우. 의도하지 않은 동작은 게임 밸런스를 무너뜨리거나 유저에게 불공정한 이점을 제공할 수 있어 즉시 등록이 필요하다.

#### 필수 기능 누락

골드 부족 시 충전 팝업이 자동으로 표시되어야 하는데 작동하지 않는 경우. 기능 자체가 빠진 경우는 유저가 정상적인 플레이 흐름을 이어갈 수 없게 만드므로 높은 우선순위로 처리해야 한다.

#### UX 관점의 사용성 문제

수량 조절 시 슬라이드 바만 존재하고 정밀 입력(숫자 직접 입력 등) 기능이 없는 경우, 기술적 오류가 아니더라도 유저의 불편을 유발하는 요소는 모두 버그로 간주하여 개선 대상에 포함시켜야 한다.

## 결함 등록 시 우선순위 / 중요도 기준

결함은 Priority(우선순위)와 Severity(심각도) 두 축으로 분류된다. 이 두 가지를 명확히 구분하여 등록해야 개발팀이 수정 순서를 올바르게 판단할 수 있다.

#### Priority(우선순위)

- Low(P4): 발생 빈도가 낮고 재현이 어려우며, 이용도가 낮은 서비스에서 발생하는 문제. 가장 나중에 처리해도 무방
- Normal(P3): 일반 기능이 정상 동작하지 않으나 대체 방안이 존재하는 경우
- High(P2): 이용도가 높은 서비스 또는 기획 이슈가 높은 기능에서 오동작이 발생하는 경우
- Urgent(P1): 서비스 진입 불가, 금전적·물리적 피해를 주는 결함. 가장 먼저 처리해야 함.

#### Severity(심각도)

- Trivial(S4): 기능에 영향 없는 사소한 디자인·UI 문제
- Minor(S3): 일반 기능 오류로 수정이 필요한 문제
- Major(S2): 주요 기능 테스트 불가. 서버 에러, 성능 저하로 정상 이용이 불가능한 문제.
- Critical(S1): 테스트 진행을 차단하거나 데이터 손실, 시스템 다운, 보안/결제 문제가 발생하는 경우

## 테스트 환경 구축

테스트 환경은 실제 유저가 게임을 경험하는 모든 조건을 재현해야 한다. OS, 하드웨어, 네트워크의 세 축을 기반으로 환경을 분류하고, 각 조건에서의 동작을 검증한다.

#### OS 분류

Windows, macOS, iOS, Android 등 운영 체제 종류에 따른 동작 검증

#### 하드웨어 분류

PC : CPU, GPU 사양별 테스트
모바일 : 삼성, LG, 화웨이, 샤오미 등 제조사 및 기기별 검증

#### 네트워크 환경 분류

WiFi, 3G, LTE 등 네트워크 조건에 따른 성능 및 안정성 테스트

## 소프트웨어 빌드 테스트 용어

#### 단위 테스트 (Unit Test)

개발자가 자신이 작성한 소스 코드를 직접 테스트하는 것. 비공식적으로 진행되며, 진행 단위는 케이스에 따라 달라진다.

#### 시스템 테스트 (System Test)

결함을 찾기 위해 소프트웨어를 실행하는 공식 테스트. 테스트 조직에서 담당하며, 요구사항 기반의 테스트 계획서를 작성하여 케이스를 설계한다.

#### 스모크 테스트 (Smoke Test)

새 빌드가 세부 테스트를 수행하기에 충분한 완성도를 갖추고 있는지 빠르게 검증하는 사전 점검 과정이다.

## 빌드 검증 테스트 | BVT (Build Verification Test)

BVT는 빌드 전반에 대한 내용을 신속하게 검증하는 테스트이다. 넓은 범위를 빠르게 확인하여 빌드의 기본적인 동작 여부를 판단하며, 이후 심층 테스트의 진행 여부를 결정한다.

#### 자동화 우선

설치·삭제 자동화 등으로 테스트를 효율적으로 수행. 반복적인 설치·삭제 과정 자동화로 인적 오류 감소 및 일관된 검증 결과 확보 가능

#### 신속한 수행

수행 시간이 짧을수록 빌드 문제를 즉각 파악 가능. 통상 수십분 이내 완료가 기준이며, 시간 초과 시 개발 사이클 전체 지연 초래

#### 넓게 테스트

세부사항보다 주요 기능·시나리오를 최대한 포함. 핵심 기능 미동작 빌드에 심층 테스트 진행은 자원 낭비이므로, 넓은 범위로 통과 여부 우선 판단

#### 즉각 실패 인지

BVT 실패 시 원인을 즉시 수정하고 타협 금지. BVT 실패 방치 시 이후 테스트 결과 전체 신뢰성 붕괴 위험, 즉시 원인 파악 및 수정 필수

## BAT & 회귀 테스트

#### 빌드 수용 테스트 | BAT (Build Acceptance Test)

BVT와 동일한 개념이지만, BVT가 완료된 빌드를 QA 조직이 직접 수행하는 테스트이다. QA가 빌드를 공식적으로 '수용'할 수 있는지를 판단하는 관문 역할을 한다.

#### 회귀 테스트 (Regression Test)

소프트웨어를 수정한 이후, 이전에 수정했던 버그가 다시 살아나는 현상을 회귀 버그(Regression Bug)라고 한다. 회귀 테스트는 이러한 버그를 찾아내기 위해 수행하는 재검증 테스트로, 기존 기능의 안정성을 보장하는 데 핵심적인 역할을 한다.

## 일반적인 테스팅 방식

효과적인 테스트는 다양한 관점에서 제품을 검증한다. 기능의 정상 동작부터 비정상적 시나리오, 그리고 성능과 호환성까지 아우르는 복합적인 접근이 필요하다.

#### BAT / BVT

새 빌드가 세부 테스트를 진행할 만큼 완성도가 있는지 신속하게 검증. 통과 실패 시 해당 빌드는 반려되며, 수정 후 재검증 필수

#### Positive Test

정상적인 프로세스 진행 시 올바른 결과가 출력되는지 확인하는 테스트. 정상 흐름에서의 기대 결과를 사전에 명확히 정의해야 판정 기준으로 활용 가능

#### Negative Test

비정상적인 입력 또는 흐름에서 시스템이 어떻게 반응하는지 검증. 예외 처리 미흡 시 크래시·데이터 손실 등 심각한 결함으로 이어질 수 있어 필수 수행 항목.

#### 비기능성 테스트

기능 외 동작 항목 - 호환성, 속도, 스트레스 테스트 등 포함. 기능이 정상이더라도 성능·호환성 문제는 유저 이탈의 직접적 원인이 되므로 별도 검증 필요

## 게임 테스트의 유형

게임 QA는 일반 소프트웨어 테스트와 달리, 재미·밸런스·서버 부하까지 검증 범위가 확장됨.

#### 기능성 테스트

게임의 모든 기능이 명세서대로 정상 작동하는지 확인

#### 호환성 테스트

다양한 기기·OS 환경에서 게임이 안정적으로 구동되는지 검증

#### 메모리 누수 테스트

장시간 플레이 시 메모리가 비정상적으로 증가하는지 모니터링

#### 게임 학습 테스트

튜토리얼 및 온보딩 흐름이 신규 유저에게 직관적으로 전달되는지 확인

#### UI 테스트

버튼·텍스트·레이아웃 등 인터페이스 요소의 정상 표시 및 동작 검증

#### 퍼포먼스 테스트

FPS, 로딩 시간, 발열 등 성능 지표가 기준치 이내인지 측정

#### 설치/제거/패치 테스트

설치·삭제·업데이트 과정에서 오류 없이 정상 처리되는지 확인

#### 서버 스트레스 테스트

대규모 동시 접속 상황에서 서버 안정성과 응답 속도 검증

#### 재미 테스트

게임의 몰입감·밸런스·재미 요소가 타겟 유저 기준에 부합하는지 평가

## TC (Test Case) | 테스트 케이스

TC란 게임을 테스트할 때 무엇을, 어떻게, 어떤 결과가 나와야 하는지를 미리 정의해 놓은 문서이다. 단순히 버튼을 눌러보는 것이 아니라, 기준을 세우고 그 기준에 맞게 검증하는 것이 TC의 핵심이다. 즉, TC는 테스트를 보다 체계적으로 진행하고, 놓치는 부분 없이 품질을 확인하기 위한 설계도이다.

좋은 TC를 작성하기 위해서는 다음과 같은 역량이 필요하다.

#### 업무 경험

다양한 개발 단계와 QA 수행 경험을 통해 쌓인 현장 감각이 필요하다. 예를 들어 업데이트 직후 자주 발생하는 오류나 반복적으로 놓치는 케이스를 알고 있으면 더 현실적인 TC를 만들 수 있다.

#### 게임 지식과 경험

장르, 메커니즘, 유저 행동 패턴에 대한 깊은 이해가 필요하다. 예를 들어 RPG와 FPS는 플레이 흐름과 핵심 검증 포인트가 다르기 때문에, 게임 특성에 맞는 TC를 작성해야 정확한 테스트가 가능하다.

#### 각 파트 업무 이해도

기획, 개발, 아트, 서버 각 파트의 역할과 산출물에 대한 이해가 필요하다. 예를 들어 기획의도와 서버 처리 방식까지 함께 이해하면, 단순 기능 확인을 넘어 원인까지 추적할 수 있는 TC를 작성할 수 있다.

## TC 작성 예시 | 목적 및 Test Basis

테스트 목적 : 캐릭터 명 생성 기능에 대한 종합 검증이다.

Test Basis가 불명확하면 테스터마다 판단 기준이 달라져 동일한 케이스에서도 Pass/Fail 결과가 엇갈릴 수 있다.

> Test Basis (테스트 기반 명세)
> - 캐릭터 명은 최소 영문 4자 / 한글 2자, 최대 영문 8자 / 한글 4자까지 입력 가능하다.
> - 영문, 한글, 숫자를 제외한 특수문자(공백 포함)는 사용이 불가하다.

Test Basis는 TC 작성의 출발점이다. 명세서에서 허용 조건과 제한 조건을 명확히 추출한 후, 이를 기반으로 Positive 및 Negative 케이스를 체계적으로 설계한다. 위에서는 '최소/최대 글자 수'와 '허용 문자 종류'가 핵심 기준이며, 이 두 조건에서 Positive(정상 입력)와 Negative(비정상 입력) 케이스가 각각 도출된다.

- Positive 케이스 예시 : 영문 4자~8자, 한글 2자~4자 범위 내 정상 입력
- Negative 케이스 예시 : 영문 3자(최소 미만), 한글 5자(최대 초과), 특수문자 포함 입력

## TC 작성 예시 | Positive 테스트

Positive 테스트는 명세서에 정의된 **정상 조건**에서 기능이 올바르게 동작하는지 확인한다. 경계값(최소/최대)을 반드시 포함해야 한다.

#### 영문 4자 생성 시도

최소 길이(영문 기준) 경계값 검증 - 정상 생성 확인

#### 한글 2자 생성 시도

최소 길이(한글 기준) 경계값 검증 - 정상 생성 확인

#### 영문 8자 생성 시도

최대 길이(영문 기준) 경계값 검증 - 정상 생성 확인

#### 한글 4자 생성 시도

최대 길이(한글 기준) 경계값 검증 - 정상 생성 확인

## TC 작성 예시 | Negative 테스트

Negative 테스트는 허용 범위를 벗어난 비정상 입력에서 시스템이 적절히 처리하는지 검증한다. 보안 취약점과 예외 케이스 중심으로 설계된다.

**최소 길이 미만 입력** - 영문 4자 / 한글 2자 미만으로 생성 시도
**최대 길이 초과 입력** - 영문 8자 / 한글 4자를 초과한 캐릭터 명 생성 시도
**공백 문자 삽입** - 맨 앞, 중간, 맨 뒤에 공백 삽입 시도
**특수문자 입력** - 사칙연산 기호, ' < > { } 등 스크립트 관련 기호 위주로 검증
**중복 캐릭터 명 입력** - 이미 존재하는 이름으로 생성 시도
**금지어 입력** - 비속어, NPC명, '운영자'등 금지 키워드 입력 시도

## TC 작성 예시 | 실제 사례 확인

실제로 사용된 TC를 한 번 살펴본다

이론으로 익힌 Positive / Negative 설계 원칙이 실무 TC에서 어떻게 구현되는지 확인한다. 실제 TC는 단순 항목 나열을 넘어, 테스트 목적 → 환경 → 절차 → 기대 결과 → 실제 결과의 구조로 기록되어야 한다. 잘 작성된 TC는 누가 수행해도 동일한 품질의 결과를 도출할 수 있어야 한다.

> 실제 프로젝트에서 사용된 TC 문서를 함께 검토하며 작성 기준과 완성도를 직접 확인해본다.

## TC 실제 예제 | 로그인 기능

로그인은 게임 진입의 첫 관문으로, 항상 로그인부터 비정상 입력, 보안 처리까지 폭 넓게 검증해야 한다.

> Test Basis
> - 아이디는 영문+숫자 조합, 4~12자
> - 비밀번호는 영문+숫자+특수문자 조합, 8~16자
> - 5회 연속 로그인 실패 시 계정 잠금 처리
> - 소셜 로그인(Google, Apple) 지원

## TC 실제 예제 | 아이템 구매 기능

상점 구매는 재화 차감, 아이템 지급, 예외 처리까지 다양한 시나리오를 포함하며, 경제 시스템과 직결되어 높은 우선순위로 검증해야 한다.

> Test Basis
> - 골드(무료 재화)와 캐시(유료재화) 두 종류의 재화 존재
> - 구매 시 보유 재화가 가격 이상이어야 함
> - 구매 완료 시 아이템은 인벤토리에 즉시 지급
> - 인벤토리 최대 보유 수량 초과 시 구매 불가
> - 이미 보유한 아이템은 중복 구매 불가

## TC 실제 예제 | 레벨업 기능

레벨업은 경험치 누적, 스탯 상승, 보상 지급이 연쇄적으로 발생하는 복합 기능이므로, 각 단계가 정확히 처리되는지 꼼꼼히 검증해야 한다.

> Test Basis
> - 경험치가 현재 레벨의 요구치에 도달하면 자동 레벨업
> - 레벨업 시 HP·공격력·방어력 스탯 자동 상승
> - 레벨업 보상(골드, 아이템)은 우편함으로 자동 발송
> - 최대 레벨(Lv. 100) 도달 시 경험치 획득 중단
> - 레벨업 연출(이펙트·사운드) 출력 후 결과 팝업 표시
