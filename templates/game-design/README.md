# 게임 기획서 작성 규칙

포트폴리오/보고 용도로 게임 프로젝트 기획 문서를 작성할 때 아래 3단계 구조를 따릅니다. 각 프로젝트 폴더(`projects/unity/<프로젝트명>/`)에 이 구조를 그대로 복사해서 채워 넣습니다.

## 구조

```
01-concept.md          # 1차: 컨셉 기획서 — 이 게임이 무엇인지, 왜 만드는지
02-system-content.md   # 2차: 시스템/컨텐츠 기획서 — 컨셉을 구현할 시스템과 콘텐츠 구조
03-detail/             # 3차: 세부 항목 기획서 — 시스템별 상세 스펙
  ui.md
  character.md
  balance.md
  data.md
  music.md
  design.md
```

## 단계별 목적

| 단계 | 문서 | 목적 |
| --- | --- | --- |
| 1차 | `01-concept.md` | 게임의 정체성(장르/타겟/핵심 재미)을 한 문서로 정리. 이후 모든 문서의 기준점 |
| 2차 | `02-system-content.md` | 1차 컨셉을 실현할 시스템 목록과 콘텐츠 구조를 정의 |
| 3차 | `03-detail/*.md` | 2차에서 정의한 시스템 각각을 실제로 구현 가능한 수준까지 구체화 (UI, 캐릭터, 밸런스, 데이터관리, 음악, 디자인 등, 필요에 따라 항목 추가) |

- 새 프로젝트를 시작할 땐 이 폴더 전체를 `projects/unity/<프로젝트명>/`으로 복사한 뒤 채웁니다.
- 3차 항목은 프로젝트마다 필요한 것만 선택해서 채우고, 목록에 없는 항목(예: 사운드 이펙트, 로컬라이제이션)이 필요하면 같은 형식으로 `03-detail/` 아래에 추가합니다.

## 참고 자료

각 단계 작성 시 이론적 근거나 아이디어가 필요하면 [`library/게임기획교육자료(1)`](../../library/게임기획교육자료(1)/README.md)의 게임 기획 강의 노트를 참고합니다.

## 제작 규칙

### 1. 단계 진행 조건

다음 단계로 넘어가려면 이전 단계의 핵심 항목이 채워져 있어야 합니다. 핵심이 아닌 항목은 `(추후 채움)`으로 남겨둔 채 진행해도 됩니다.

| 전환 | 필수(핵심) 항목 | 비워둬도 되는 항목 |
| --- | --- | --- |
| 1차 → 2차 | 로그라인, 기획 의도, 핵심 재미, 핵심 컨텐츠/파생 컨텐츠, 핵심 시스템(개요), 핵심 루프, 경쟁작·차별점(포지셔닝), MVP 범위 | 아트 스타일 레퍼런스, 세계관/스토리 개요, 리스크/도전 과제, 일정 개요 |
| 2차 → 3차 | 시스템 목록(전 행의 목적·우선순위), 우선순위 "상" 시스템의 흐름 | 우선순위가 낮은 시스템의 세부 흐름, 콘텐츠 구조 수치 |
| 3차 (착수한 파일) | 착수한 `03-detail/*.md` 파일은 표/섹션에 빈칸 없이 완성 | 프로젝트에 필요 없는 항목 파일 자체를 만들지 않는 것은 허용 |

- `projects/unity/README.md`의 "상태" 컬럼은 현재 도달한 최고 단계로 갱신합니다: `컨셉 단계` → `시스템 단계` → `세부 기획 단계` → `완료`.
- 빈 항목은 절대 그냥 비워두지 말고 `(추후 채움)`으로 명시합니다. 검색(`추후 채움`)으로 미완료 항목을 언제든 찾을 수 있게 하기 위함입니다.

### 2. 버전/개정 이력 규칙

- `v0.x`: 초안/작업 중 (핵심 항목 미완성, `(추후 채움)` 존재 가능)
- `v1.0`: 해당 문서의 핵심 항목이 모두 채워진 시점
- `v1.x`: v1.0 이후의 부분 수정
- 버전을 올릴 때마다 문서 맨 아래 `## 개정 이력` 표에 한 줄을 추가합니다.

| 버전 | 날짜 | 변경 내용 |
| --- | --- | --- |
| v0.1 | YYYY-MM-DD | 최초 작성 |

### 3. 커밋/history 기록 연동 규칙

- 기획서 관련 커밋 메시지는 `docs: <프로젝트명> <문서명> ...` 형태로 씁니다 (예: `docs: beat-puzzle-rpg 01-concept v1.0 (일정/리스크 채움)`).
- **버전이 올라가는 커밋**(예: v0.1 → v1.0)만 `history/YYYY-MM.md`에 기록합니다. 오탈자 수정처럼 버전이 그대로인 사소한 변경은 history 기록을 생략해도 됩니다.
- history 기록 시 "어떤 프로젝트의 어떤 문서가 몇 버전이 됐는지"를 한 줄로 남깁니다.

### 4. 새 프로젝트 생성 절차

1. `templates/game-design/` 폴더 전체를 `projects/unity/<프로젝트명>/`으로 복사합니다.
2. 각 파일의 `[프로젝트명]`, `YYYY-MM-DD`, `v0.1` 등 메타 자리표시자를 실제 값으로 채웁니다.
3. `projects/unity/README.md`의 목록 표에 프로젝트 행을 추가합니다 (상태: `컨셉 단계`).
4. 최초 커밋 메시지: `docs: <프로젝트명> 컨셉 기획서 초안 추가` 형태로 남기고, `history/`에도 기록합니다.

### 5. 기획서 파일 생성 규칙

- `03-detail/`에 목록에 없는 항목(예: 사운드 이펙트, 로컬라이제이션)을 추가할 때 파일명은 영어 소문자 kebab-case로 짓습니다 (예: `sound-effect.md`, `localization.md`).
- 새로 만든 파일도 기존 `03-detail/*.md`와 동일하게 제목 · `작성일`/`버전` 메타 · `연관 문서` 링크 · `개정 이력` 표 구조를 갖춥니다.
- 파일 안의 표/섹션에 아직 채우지 않은 칸은 삭제하지 말고 빈 칸 또는 `(추후 채움)`으로 남겨 미완료 상태임을 드러냅니다.

### 6. 컨셉 기획서(01-concept.md) 표준 목차

`library/게임기획교육자료(1)/`의 컨셉·GDD·마케팅 관련 강의 노트를 근거로 정리한 목차입니다. 순서와 필수 여부는 아래를 기준으로 합니다.

| 순서 | 항목 | 필수/선택 | 근거 요약 |
| --- | --- | --- | --- |
| 1 | 한 줄 소개(로그라인) | 필수 | "테마→경험+메커니즘→장르" 공식으로 한 문장 요약 (`26-02-10-concept-worldbuilding`) |
| 2 | 기획 배경(기획 의도) | 필수 | 목적·대상·핵심 경험 3요소, 불필요한 기획을 걸러내는 필터 역할 (`26-02-09-content-design`, `26-02-10-concept-worldbuilding`) |
| 3 | 핵심 재미 (Core Fun) | 필수 | 컨셉 3요소 중 경험(Experience)+메커니즘(Mechanism) (`26-02-10-concept-worldbuilding`) |
| 4 | 핵심 컨텐츠 / 파생 컨텐츠 | 필수 | "컨셉 기획에서 정해야 하는 것들" 중 하나 — 핵심 컨텐츠의 성공이 곧 게임의 성공 (`26-02-10-concept-worldbuilding`) |
| 5 | 핵심 시스템 (개요) | 필수 | 위 컨텐츠를 구현할 시스템을 이름 단위로만 나열(상세 흐름·우선순위는 2차 문서로 위임) (`26-02-10-concept-worldbuilding`) |
| 6 | 핵심 루프 (Core Loop) | 필수 | "플레이어가 반복하는 게임의 심장박동" (`26-02-10-concept-worldbuilding`) |
| 7 | 경쟁작/유사 게임 분석 & 차별점(포지셔닝) | 필수 | STP·포지셔닝, OPP 패턴의 "유사 제품 분석" 단계 (`26-06-02-marketing-theory`, `26-05-28-game-marketing`) |
| 8 | 세계관 / 스토리 개요 | 선택 | 상세 설정보다 플레이로 드러나는 핵심 갈등 한두 줄 우선(Play>See>Write) (`26-02-11-storytelling`) |
| 9 | 아트 스타일 / 무드 레퍼런스 | 선택 | — |
| 10 | 개발 범위(스코프/MVP) | 필수 | 기존 규칙 유지 |
| 11 | 리스크 / 도전 과제 | 선택 | 기존 규칙 유지 |
| 12 | 일정 개요 | 선택 | 기존 규칙 유지 |
| 13 | 개정 이력 | 필수(형식) | 기존 규칙 유지 |

- 수익 모델·지표(DAU 등)는 별도 유료화/사업 문서 영역으로 보고 컨셉 기획서에는 포함하지 않습니다 (`26-06-01-game-design-document`가 유료화·경제 문서를 별도 타겟 문서로 분리).
- "핵심 시스템(개요)"과 2차 문서(`02-system-content.md`)의 시스템 목록은 상세도로 구분합니다: 1차는 이름+한 줄, 2차는 목적·우선순위·흐름까지.
